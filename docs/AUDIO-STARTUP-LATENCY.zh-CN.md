# 红键到首帧输出的启动延迟

## 结论与证据边界

本轮未连接真实 G10、发送真实 GATT 命令或打开音频流。旧版只读。用户确认新版从 `desktop-ui/start_g10_control.cmd` 源码入口运行。

**没有找到“新版每次红键多做一次枚举/能力检查/音频流初始化”的代码回归，也不能凭现有日志确定用户感受到的慢半拍主要发生在哪段。** 找到并移除了两版共有的同步日志阻塞：WinRT 通知回调先完成 JSONL 磁盘写入，随后才能把 START/音频送入解码队列，并投递协议控制回调。解码会话开始日志也可能等待同一把日志锁。不同磁盘状态、日志目录或系统负载可能放大此阻塞，但这只是待实机验证的解释。

新增分段时间戳供本机验证。它们测量主机回调边界，不测量遥控器物理按键、电波传输之前的时间、DAC 播放或目标应用开始识别的时间。

## 两版逐段对照

| 阶段 | 代码对照结果 | 判断 |
|---|---|---|
| 能力协商 | `Controller.initialize` 在连接后发一次 GET_CAPABILITIES，红键处理不重新调用；新版兼容性检查是用户显式连接前操作 | 未发现每次红键新增检查 |
| 设备枚举、地址和音频路由复核 | 新版新增身份/路由校验在监督器启动、桥接启动和 `observe` 初次打开设备时执行 | 影响连接准备时间，不串行参与已就绪红键首帧 |
| ATVV MIC_OPEN | 两版 `Controller.receive` / `tick` 相同。08 请求才入队 MIC_OPEN，仍受原有能力、命令白名单、STOP 取消和超时检查约束 | 没有更改命令或跳过校验 |
| 100 ms 协议轮询 | 两版 `observe` 都每 100 ms 执行一次 `tick`。若设备走 08→OPEN 路径，可能有 0–100 ms 排队等待 | 两版共有；现有选定日志没有 OPEN，未据此修改协议调度 |
| 音频输出流 | 两版都是连接期间创建并启动一次 48 kHz 双声道 WASAPI 输出流，红键只重置软件缓冲和解码状态 | 未发现每次红键重复创建流 |
| 队列和首帧 | 两版解码队列容量 64、阻塞 `get(timeout=.1)`，有数据会立即唤醒，并非固定等待 100 ms；均保留 START 前 50 ms 内的音频帧 | 没有新增首帧等待 |
| 预缓冲 | 两版 48 ms，即 2304 个 48 kHz 帧；128 字节 ADPCM 帧产生 256 个 16 kHz 样本，重采样后 768 帧，需要三包才达到阈值 | 保留原值；16 ms 间隔输入时，从第一包到第三包约 32 ms，再等下一输出回调 |
| 输出块 | 两版 `blocksize=480`，对应 10 ms 软件块；WASAPI/驱动的额外延迟尚无本轮实测 | 保留原值，不推导实际 VB-CABLE 端到端延迟 |
| 解码表 | 新版把旧版从参考源码读取的 IMA 表改为本地常量；算法仍相同，避免每次 START 时读外部表文件 | 无证据表明此差异导致变慢 |
| 日志 | 两版原先均在通知进解码队列前同步写盘，逐行缓冲；控制与解码日志还会争用锁 | 本轮消除这个可复现阻塞 |
| 监督器/状态刷新 | 与桥接在不同进程；新增配置/证明读取不直接调用实时解码。桥接每 200 ms 写状态、前端每秒刷新，原有节奏未变 | 状态显示可以晚于实际音频；磁盘/CPU 竞争只属可能因素，没有受控 A/B 证据 |
| 自动唤起 | 两版自动模式均有前台准备及目标录音通道确认，确认前软件输出闸门关闭；手动模式无此闸门 | A/B 应使用同一模式，并提前开启目标应用录音来隔离本次链路 |

## 读取已有真实运行日志

只读取已有 JSONL 元数据，没有重放录音或启动设备。`%LOCALAPPDATA%/G10Control/logs/bridge-20261020-221427-495120/events/events.jsonl` 中的 8 个 START：

- GET_CAPABILITIES 共 1 次，MIC_OPEN 为 0 次。
- START 回调到 `pcm_session_start`：约 0.139–0.445 ms。
- START 回调到其后首个音频通知：约 0.160–17.096 ms。

这些是旧有日志的真实主机时间差。`pcm_session_start` 表示解码状态已初始化，不等于首帧已解码或已输出；首个音频回调也可能先于 START。日志没有物理按键/首 PCM/首次输出回调的完整时间戳，且运行记录缺少严格的源码版本标记，不能据日期当作受控的新旧版本性能对照。

## 本轮最小优化与观测

`g10_audio_bridge.py`：

- 仅实时桥接的 `LiveRecorder` 使用独立日志线程，最多排队 512 个元数据事件；生产端保留原始 `perf_ns`/`unix_ns`，不等磁盘写入。写盘不持有音频通知计数锁，不保存原始音频。
- 日志队列满或写入失败会记录错误、触发安全停止；日志异常不会从 BLE 清理块抛出，CCCD 恢复和资源释放仍可执行。安全退出时排空日志，再汇总计数；不把缺失证据当成成功。
- START、首个音频通知、首 PCM 入缓冲、首个输出回调拷贝 PCM 分别计时。`AudioBuffer` 的输出采样、门控、阈值、溢出和尾部排空规则未改动。
- 常规状态循环在观察到首输出后，异步写一条 `audio_startup_timing`；不从音频回调写日志。最后一次会话也保存在 `bridge-summary.json` 的 `last_startup_timing`，当前会话保存在桥接状态 JSON 的 `startup_timing`。极短会话可能早于状态循环观察而结束，应同时查看最后一次汇总。

未改动 ADPCM 算法、重采样公式、增益、WASAPI 参数、VB-CABLE 选择或 ATVV 字节/安全条件。

## 离线计时与回归

新增 `measure_startup_latency.py`：只解析旧版四个桥接类，在隔离命名空间中运行；不导入旧版模块，不生成旧版 pycache，不执行入口。两种实现使用相同解码器，隔离日志调度的影响。三包音频作为合成突发送入真实软件解码/缓冲，输出是 NumPy 内存数组，不是音频设备。

```powershell
.\.venv\Scripts\python.exe measure_startup_latency.py --old-root ..\diagnostic-3k --rounds 10
```

本轮 10 次的主机墙钟中位数：

| 场景 | 旧版同步日志 | 修改后 |
|---|---:|---:|
| 不注入写盘延迟 | 1.317 ms | 1.013 ms |
| 每次元数据写盘注入 20 ms | 103.662 ms | 0.958 ms |

**20 ms 是人为注入，不是对本机磁盘的测量；三包突发也不模拟真实 BLE 间隔。** 结果证明日志变慢时不再阻塞首 PCM/内存输出，不能解释为真实 G10 已减少约 100 ms。

新增 `test_startup_latency.py` 验证：阻塞日志线程时首帧仍可解码/输出；生产端时间戳与日志计数保留；写盘失败/队列溢出触发停止；48 ms 阈值不变；START 前音频仍保留；分段时间戳及会话重置正确。使用虚拟时钟的三包 16 ms 间隔测试中，首次内存输出回调设在 START 后 40 ms，断言得到 40 ms；该数值是模拟输入，不是实测无线延迟。

回归结果：根目录 124 项、桌面运行层 45 项、前端 12 项全部通过，TypeScript/Vite 构建通过。

## 本机验收

1. 从新版 `desktop-ui/start_g10_control.cmd` 启动，连接后等 ATVV 已就绪。比较时保持同一音频路由、增益和唤起模式，提前在目标应用开启 CABLE Output 语音输入，先隔离自动唤起/手动操作时间。
2. 每次按住红键立即说同一句短语，持续约 2 秒，松开，间隔后重复至少 10 次，最后安全停止。关注句首是否完整和起音反应，不使用前端状态亮起时间代替音频时间。
3. 读取本次 `logs/bridge-*/events/events.jsonl` 中 `audio_startup_timing`，对比这些字段：
   - `start_to_first_audio_ms`：主机收到 START 到首音频通知，可能为负（音频先到）。
   - `first_audio_to_pcm_ms`：包含队列等待、等待 START/凑齐首帧和首帧解码。
   - `first_pcm_to_output_callback_ms`：包含剩余预缓冲、自动模式闸门和回调等待。
   - `start_to_output_callback_ms`：START 到首 PCM 被复制进输出回调，总体主机启动时间。
4. 若以上时间都小但仍明显感觉慢，下一步应测物理红键到 START，以及输出回调之后的 VB-CABLE/目标应用录音与识别启动；当前计时无法判定这两端的延迟。本轮没有进行这些实机操作。
